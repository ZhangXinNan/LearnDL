# LearnDL 版本号与迭代规范

> 文档版本：V1.1  
> 状态：正式基线（精简修订）  
> 修订日期：2026-10-16  
> 关联文档：[项目目标与基本要求](目标要求.md) · [学习与开发流程](开发流程.md)

## 1. 版本的作用

LearnDL 是个人长期学习项目。项目版本标识的是**已经完成并通过验证的一个小目标**，不是软件成熟度、学习天数、提交次数或知识水平。

**规则：每次完成一个可独立验收的基本功能或学习小目标，项目版本增加 `0.1`。** 不使用三级版本号（例如 `v0.0.1`、`v0.1.1`），也不套用要求主版本表示重大变更的语义化版本规则。

## 2. 版本格式与进位

项目版本采用 `v主版本.次版本`，例如：

```text
v0.1 → v0.2 → … → v0.9 → v1.0 → v1.1 → … → v1.9 → v2.0
```

- **`v0.0` 是唯一的初始化封版例外**：用于确认项目定位、目标、学习流程和版本规范已准备就绪，不代表完成任何算法学习目标，也不占用 `0.1` 迭代。
- 第一个完成的小目标发布为 `v0.1`。
- 每完成一个后续小目标，版本前进一步。
- 次版本数字只使用 `0`–`9`，到 `v0.9` 后进位为 `v1.0`；不写 `v0.10`。
- `v1.0` 仅是进位后的下一次迭代，**不代表项目毕业、正式上线或所有知识学完**。
- Git 标签统一使用小写 `v` 前缀（如 `v0.3`）。

## 3. 版本粒度

每个版本只能有**一个主目标**，例如：

- 实现并验证一个前向传播函数。
- 完成一种梯度计算方法的推导和验证。
- 分析一个超参数对实验结果的影响。
- 测出一种推理实现的基本性能基线。

一个目标可以包含必要的原理说明、代码、测试、可视化和总结，但不应把互不相关的多个学习目标打包。目标太大就拆分，目标小而可验收即可，不人为要求每版工作量一致。

通常**不单独升版本**的情况：修复当前目标的 Bug、完善测试或笔记、整理代码、修改配置、尝试但尚未得到可验收结果。若“定位并解决某个问题”本身就是明确的小学习目标，则可以单独成版。

## 4. 何时发布版本

一个小目标完成后，按以下顺序发布：

1. 对照事先定义的验收条件，确认结果与证据充分。
2. 完成必要的学习总结，将代码、推导、测试或实验记录保存好。
3. 在根目录 `CHANGELOG.md` 增加该版本记录。
4. 提交相关变更，再创建对应 Git Tag（例如 `v0.3`）。

**未通过验收就不发布。** 学习过程中可自由多次提交，提交数与版本号无关。发现已发布成果存在重要问题时，记录更正并在后续工作中修复；不随意改写已发布的 Git Tag。

## 5. 最小版本记录

`CHANGELOG.md` 只需按版本记录以下信息，通常放最新版本在前：

```markdown
## v0.X — 小目标名称

- **目标：** 本次完成的一个小目标。
- **成果：** 代码、推导、实验或笔记的位置。
- **验收：** 使用什么证据确认通过。
- **遗留问题：** 无 / 尚待解决的问题。
```

无需为每次普通提交、修正或学习中间过程编写发布公告。完整的原理、实验和总结放在该版本的学习记录中，`CHANGELOG.md` 只作索引。

## 6. 区分项目版本与规范文档版本

这两类版本**相互独立**：

| 类型 | 例如                            | 表示什么 |
| --- |-------------------------------| --- |
| 项目学习版本 | `v0.1`、`v0.2`、`v1.0`          | 完成并验收的小学习目标，使用 Git Tag。 |
| 规范文档版本 | `目标要求.md` V1.1、`开发流程.md` V1.1 | 文档本身的修订记录，不表示学习进度。 |

更新目标、流程或版本规范的措辞，不应自动让学习项目版本增加 `0.1`。规范文件有实质改动时更新自身文档版本即可。

## 7. 长期维护约定

- 一人维护，优先简单、清晰、易追溯；不强制复杂发布流程。
- 不一次规划大量固定版本；下一小目标可在当前成果基础上再确定。
- 已完成的最高 Git Tag 是项目版本的主要依据；尚无 Tag 时可参考 `CHANGELOG.md` 的最新已验收记录。
- 每个版本**如何学习、实现、验证与总结**，统一遵循 [`开发流程.md`](开发流程.md)，本文件不重复定义七步流程。

---

**一句话规则：一个小目标，一次验收，一个 `0.1` 版本。**
