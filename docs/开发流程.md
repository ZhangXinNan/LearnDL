# LearnDL 学习与开发流程

> 文档版本：V1.1  
> 状态：正式基线（精简修订）  
> 修订日期：2026-10-16  
> 关联文档：[项目目标与基本要求](目标要求.md) · [版本与迭代规范](版本规范.md)

## 1. 用途

本文件定义 LearnDL **每次学习或实践如何完成一个小目标**。项目由一个人长期维护，流程的作用是帮助真正理解算法、保留验证证据和学习成果，而不是增加管理工作。

> **一个小目标 → 理解原理 → 选择简单方法 → 亲自实践 → 验证与分析 → 总结。**

默认采用七步；**七步是思考和检查顺序，不是七份文档**。可以根据理论、实现、实验或优化目标调整和合并步骤。遇到错误可以返回前面的步骤。

## 2. 七步流程

```text
① 目标与验收
       ↓
② 原理说明
       ↓
③ 方案与实现方法
       ↓
④ 实践 / 代码实现（按目标需要）
       ↓
⑤ 测试、验证与结果分析 ── 未通过 → 返回② / ③ / ④
       ↓
⑥ 可视化（按需）
       ↓
⑦ 总结与归档
```

### ① 目标与验收

**回答：这次只做什么，做到什么程度算完成？**

- 明确一个主目标，必要时写明不做什么；过大就拆分。
- 说明问题、输入输出、约束及预期成果；选择合适的评价指标或比较基线。
- 预先写出通常 1–3 条可检查的验收条件。

**最小产出：** 一句话目标与验收条件。

### ② 原理说明

**回答：为什么这样做，核心计算是怎样发生的？**

- 解释概念、算法机制、关键公式和变量或张量维度（如适用）。
- 说明主要假设、适用范围、局限；对关键推导自行验证。
- 按需补充相关数学，关注可能的数值稳定性问题，不无限扩展背景学习。

**最小产出：** 未来的自己也能看懂的简要原理说明、推导或示例。

### ③ 方案与实现方法

**回答：怎样用最简单、最清晰的方法达到目标？**

- 依据学习目的选择 Python、C++ 或其他语言，以及 NumPy 等适当工具；PyTorch 可以辅助数值对照和验证，但不以复现完整模型为 LearnDL 的主线。
- 简要说明核心步骤、输入输出、必要依赖以及如何验证。
- 优先最小实现，少封装、少依赖；只有在学习需要时深入底层或优化性能。

**最小产出：** 几行方法说明和验证思路，无需单独设计文档。

### ④ 实践 / 代码实现

**回答：能否亲自完成最关键的工作？**

- 算法目标：实现关键计算路径，保证逻辑清楚、可运行。
- 理论目标：可通过自主推导、例题或手算完成，无须强行写代码。
- 实验目标：可以复用已有实现，不必重复编写相同模块。
- 遇到报错、异常或意外结果，先定位原因、修复并记录关键经验；避免过早抽象或引入复杂架构。

**最小产出：** 与目标对应的代码、推导或实验操作记录。

### ⑤ 测试、验证与结果分析

**回答：凭什么认为结果正确？实验说明了什么？**

- 选择与目标匹配的证据：手算/已知结果、单元测试、参考实现、梯度检查、边界测试或对照实验。
- 数值比较使用合理容差；必要时检查精度、稳定性、计算顺序等因素。
- 重要实验记录数据来源、配置、随机种子、运行环境与结果，保证合理可复现。
- 性能优化先测基线，固定可比条件，记录延迟、吞吐量或内存等指标，同时检查正确性和精度。
- 分析观察到的现象、可能原因和局限；如果不符合验收标准，回到前面的步骤修正。

**最小产出：** 验证方法、关键结果、解释，以及通过/未通过结论。

### ⑥ 可视化（按需）

**回答：图表是否比数字、文字更有助于理解？**

仅在有价值时绘制曲线、计算图、误差分布、模型结构或性能对比；标注坐标、单位与条件。能用数值表或文字说清楚时，**直接跳过**。结果分析已经属于第⑤步，不能因为不绘图而省略。

**最小产出：** 有必要时的图表及简短解释；否则无须产出。

### ⑦ 总结与归档

**回答：真正掌握了什么，还有什么不理解？**

- 用自己的话总结原理、实现选择、验证证据、关键问题及局限。
- 适当标注掌握深度（参考 [`目标要求.md`](目标要求.md) 中的 L1–L5）；记录遗留问题，但不强制纳入当前版本。
- 验收通过后记录成果并按 [`版本规范.md`](版本规范.md) 发布版本；**未通过验收不发布**。

**最小产出：** 简短总结、验收结论及成果位置。

## 3. 不同小目标的应用

| 类型 | 重点 | 允许省略或简化 | 必须有的证据 |
| --- | --- | --- | --- |
| 算法实现 | 原理、关键计算、正确性 | ⑥ 可视化 | 实现、测试或参考对照、结论 |
| 理论理解 | 解释、推导、具体例子 | ③ 简化、④ 代码、⑥ 可视化 | 独立说明、推导/例题验证、结论 |
| 对照实验 | 假设、变量、指标、结果分析 | 重复实现可省略、⑥ 视需要 | 可复现条件、数据、解释 |
| 推理优化 | 正确性、性能基线、公平测量 | 无关原理推导、⑥ 视需要 | 前后测量、环境条件、精度或正确性检查 |

**不可省略的是：明确目标、合适的验证证据、能够解释的结论。** 其余步骤按实际需要灵活安排。

## 4. 最小记录方式

默认**每个版本一份 Markdown 学习记录**，其他代码、测试或图表只在有需要时单独存放。不必为七个步骤创建七个文件。

```markdown
# v0.X — 小目标名称

## 目标与验收
- 目标：
- 完成条件：

## 原理与方法
- 核心原理 / 关键公式：
- 实现或实验方法（语言、库、步骤及理由）：

## 实践与验证
- 代码 / 推导 / 实验位置：
- 验证方法、结果与分析：
- 可视化（仅有必要时）：

## 总结
- 我理解了什么：
- 局限与待解决问题：
- 掌握等级（可选）：
- 验收：通过 / 未通过
```

很简单的目标可以进一步合并标题；较复杂的目标可以追加公式、表格或链接。不要为了填模板而制造内容。

## 5. 完成一次学习迭代的最小检查

- [ ] 主目标和验收条件清楚。
- [ ] 能自己解释核心原理或方法。
- [ ] 留下与目标匹配的实现、推导或实验成果。
- [ ] 验证达到标准；重要结果可合理复现，问题和局限有解释。
- [ ] 留下简短总结和必要的成果位置。
- [ ] 验收通过后按版本规范记录并打 Git Tag。

## 6. 个人维护原则

- 不强制 Issue、PR、复杂分支、代码评审或项目管理平台；按需使用即可。
- 允许反复试错、多次提交；代码和记录以**清楚、易理解、容易再次运行**为先。
- 不强制统一语言、框架或复杂目录；只有产生真实维护需要时才抽取公共代码。
- 不为每个练习生成长报告；能引用的资料不重复抄写。
- 一次目标没完成就继续完善，不为了赶版本而降低验证标准。
