# 深入理解 DeZero：Variable 与 Function 的设计本质

我仔细看了你上传的 v0.3 `core.py`。

我觉得你现在到了一个非常关键的学习节点：能看懂代码，不等于已经建立了对整个系统的心智模型。

你可能知道 `Variable` 保存什么、`Function.__call__()` 做什么、`backward()` 怎么运行，但如果不看代码，能否从零想象出整个自动微分框架是怎样运转的？

今天我们换一种方式。

不按照代码顺序解释，而是从设计者的角度出发：假设我们要从零发明 DeZero，为什么最终会设计出 Variable 和 Function 这两个类？

## 一、先忘记代码：我们究竟要解决什么问题？

假设有一个数学表达式：

$$
y=(x^2+3x)^2
$$

如果 $x=2$，我们当然能够使用 NumPy 计算出 $y=100$。

但深度学习框架不只需要计算函数值，还需要自动得到：

$$
\frac{dy}{dx}
$$

进一步还希望计算：

$$
\frac{d^2y}{dx^2}
$$

我们希望达到这样的效果：

```python
x = Variable(np.array(2.0))
y = (x**2 + 3*x)**2
y.backward()
print(x.grad)
```

用户只需要像写数学公式一样写 Python 表达式，框架就能够自动求导。

那么问题来了：

计算机只知道如何执行加法、乘法、平方，怎么知道这些操作之间的数学关系，又怎么自动求导？

这才是设计 Variable 和 Function 的根本动机。

## 二、如果只允许设计两个类，我会怎么设计？

答案就是你现在代码中的两个角色。

Variable

带有来源记录的数据

我存着什么值？我的梯度是多少？我是谁计算出来的？

Function

知道如何计算和求导的运算节点

我接收了哪些输入？产生了哪些输出？局部梯度怎么计算？

Variable 负责保存值与依赖关系，Function 负责执行运算与提供局部求导规则。

这是一种非常重要的职责分离。

### 1. Variable：不只是一个数字，而是一个有履历的数字

你现在的 `Variable` 核心成员是：

```
class Variable:
    def __init__(self, data, name=None):
        self.data = data
        self.name = name
        self.grad = None
        self.creator = None
        self.generation = 0
```

它们可以这样理解：

| 成员           | 直观意义                  |
| ------------ | --------------------- |
| `data`       | 我现在的数值                |
| `grad`       | 对指定最终输出反向传播后，我收到的累计梯度 |
| `creator`    | 是哪个 Function 创造了我     |
| `generation` | 我在计算图中位于第几代           |
| `name`       | 我的可选名称，便于识别           |

注意 `grad` 并不是这个变量天生就有的属性值。

例如，同一个 $x=2$：

对于 $y=x^2$，它的梯度是 4。

对于 $z=x^3$，它的梯度是 12。

所以 `x.grad` 的真正含义是：当前这次反向传播所选择的输出，相对于 x 的梯度。

Variable 最关键的设计其实不是 `data`，而是：

```python
self.creator = None
```

为什么？

因为一旦一个变量知道自己是被谁创造的，就可以一路追溯自己的计算来源。

一个普通数字：

```
a = 4.0
```

只知道自己是 4。

一个 Variable：

```
a = Variable(np.array(4.0))
```

如果设置了 `a.creator`，它还能够知道：

“我这个 4，是某个乘法运算由两个 2 算出来的。”

这就是从普通数值变成计算图节点的关键一步。

### 2. Function：不是单纯的数学函数，而是计算过程的记录

看看你的 `Mul`：

```
class Mul(Function):
    def forward(self, x0, x1):
        return x0 * x1
    def backward(self, gy):
        x0, x1 = self.inputs
        return gy * x1, gy * x0
```

它有两种能力。

前向传播：

$$
y=x_0x_1
$$

反向传播：

$$
\frac{\partial L}{\partial x_0} = \frac{\partial L}{\partial y}x_1
$$

$$
\frac{\partial L}{\partial x_1} = \frac{\partial L}{\partial y}x_0
$$

这里用 $L$ 表示最终要求导的输出，比如神经网络的损失函数。

Function 不需要知道整个神经网络的结构，也不需要知道最终损失函数是什么。

它只需要知道：

如果有人把输出梯度 `gy` 交给我，我该怎样把梯度传给自己的输入？

这就是整个框架可以由很多简单 Function 组合成复杂神经网络的原因。

还有一个值得注意的细节：`Mul` 是运算类型，`Mul()` 创建的实例才是一次具体的运算节点。这个实例保存了这次调用的输入和输出关系。

所以你可以把 Function 理解为：一个执行过运算、记住了现场、知道如何把梯度向前传递的节点。

## 三、Variable 和 Function 怎样自动组成计算图？

这可能是整套设计中最精妙的部分。

来看一个例子：

```
x = Variable(np.array(2.0))
a = x * x
b = a * a
y = b + a
```

数学上就是：

$$
a=x^2,\quad b=a^2,\quad y=b+a=x^4+x^2
$$

前向计算：

$$
x=2,\quad a=4,\quad b=16,\quad y=20
$$

前向计算图：数据如何流动

箭头表示前向数据依赖；每次乘法、加法都是独立的 Function 实例。

这里需要理解一个本质：

这张图不是我们事先创建出来的，而是在执行 Python 表达式时自然产生的。

为什么？

因为你的 `setup_variable()` 中有：

```
Variable.__mul__ = mul
Variable.__add__ = add
```

所以：

```
a = x * x
```

本质上会执行：

```
a = mul(x, x)
```

然后：

```
def mul(x0, x1):
    return Mul()(x0, x1)
```

最后进入：

```
Function.__call__()
```

它完成了两项工作：

第一项：计算数值。

```
inputs = [as_variable(x) for x in inputs]
xs = [x.data for x in inputs]
ys = self.forward(*xs)
outputs = [Variable(as_array(y)) for y in ys]
```

这部分用 NumPy 做实际计算。

第二项：记录这次运算的来源。

```
self.inputs = inputs
self.outputs = [weakref.ref(output) for output in outputs]
for output in outputs:
    output.set_creator(self)
```

这部分把 Variable 和 Function 连接起来。

于是，一个看起来很普通的表达式：

```
a = x * x
```

执行时做了远不止一个乘法：

- 创建一个 Mul 运算实例。
- 得到计算结果 4。
- 把结果封装成新的 Variable `a`。
- 让 `a.creator` 指向 Mul。
- 让 Mul 记住输入 `x` 和输出 `a`。

这就完成了一次计算图节点的构建。

而下一次 `a * a` 又重复这个过程。

整张图因此不断生长。

这就是动态图（Define-by-Run）的本质：运行代码的同时，记录实际执行过的可微运算。

甚至可以在 Python 中使用循环和条件分支，计算图会随着实际执行的路径而改变。

## 四、反向传播：本质上是在倒着分配梯度

这是第二个最重要的理解关口。

我们已经有了计算图：

$$
x\rightarrow a\rightarrow b\rightarrow y
$$

同时，$a$ 还直接参与了 $y$ 的计算。

现在执行：

```
y.backward(retain_grad=True)
```

你可能觉得这是在“对整个表达式求导”。

但计算机实际上并不知道整个表达式的数学公式。它只知道一个个 Function 的局部求导规则。

### 1. 先理解 gy 和 gx 的真实含义

假设某个 Function：

$$
y=f(x)
$$

但最终我们关心的输出是 $L$。

那么：

$$g_y=\frac{\partial L}{\partial y}$$

$$g_x=\frac{\partial L}{\partial x}$$

链式法则告诉我们：

$$\boxed{g_x=g_y\frac{\partial y}{\partial x}}$$

这就是每个 `Function.backward()` 在做的事情。

例如：

```python
class Square(Function):
    def backward(self, gy):
        x = self.inputs[0]
        return 2 * x * gy
```

它根本不需要知道最终输出 $L$ 是什么。

只需要知道局部导数：

$$
\frac{\partial y}{\partial x}=2x
$$

然后乘上外部传进来的 `gy`。

你可以将 `gy` 想象成从后方传过来的“梯度信号”，Function 根据自己的运算规则，把信号转换为输入端的梯度。

严格来说，这是一种反向模式自动微分：复杂函数被拆成局部运算，每个节点计算其局部雅可比与上游梯度的乘积（VJP），而不是显式构造整个函数的巨大雅可比矩阵。

## 五、现在终于可以真正理解 Variable.backward() 了

你代码中最重要的两个方法，其实各自承担完全不同的工作。

| 方法                    | 核心职责                          |
| --------------------- | ----------------------------- |
| `Function.backward()` | 计算当前运算的局部梯度传播规则               |
| `Variable.backward()` | 组织整个反向传播过程，按正确顺序调用各个 Function |

前者解决数学问题，后者解决计算图调度问题。

看你的核心代码：

```
def backward(self, retain_grad=False, create_graph=False):
    if self.grad is None:
        self.grad = Variable(np.ones_like(self.data))
    funcs = []
    seen_set = set()
    def add_func(f):
        if f not in seen_set:
            funcs.append(f)
            seen_set.add(f)
            funcs.sort(key=lambda x: x.generation)
    add_func(self.creator)
    while funcs:
        f = funcs.pop()
        gys = [output().grad for output in f.outputs]
        with using_config('enable_backprop', create_graph):
            gxs = f.backward(*gys)
            if not isinstance(gxs, tuple):
                gxs = (gxs,)
            for x, gx in zip(f.inputs, gxs):
                if x.grad is None:
                    x.grad = gx
                else:
                    x.grad = x.grad + gx
                if x.creator is not None:
                    add_func(x.creator)
```

暂时忽略异常处理和梯度释放细节。这段算法其实只有三个核心动作。

### 动作 A：找到应该处理的 Function

```
add_func(self.creator)
```

从最终输出变量找到创造它的 Function。

然后，通过：

```
x.creator
```

继续找到更前面的 Function。

所以反向传播不需要从最初的输入变量开始搜索，而是从输出出发，一路沿着 `creator` 向前追溯。

`creator` 就是计算图能够被反向遍历的关键。

### 动作 B：把输出梯度传给 Function，得到输入梯度

```
gys = [output().grad for output in f.outputs]
gxs = f.backward(*gys)
```

这一步完全对应数学上的链式法则。

当前 Function 接收输出梯度 `gys`，然后用自己实现的求导规则计算输入梯度 `gxs`。

注意，反向传播不是把前向函数“反过来计算”。乘法的反向传播不是除法，而是运用乘法的求导规则。

### 动作 C：累加梯度

```
if x.grad is None:
    x.grad = gx
else:
    x.grad = x.grad + gx
```

为什么不能直接写：

```
x.grad = gx
```

因为一个 Variable 可能被多条计算路径共享。

刚才的例子里，`a` 同时参与了 `b` 和 `y` 的计算。

它接收到两部分梯度：

$$a.grad=1+8=9$$

同样，`x * x` 中的两个输入其实都是同一个 `x`，两个输入位置都要贡献梯度。

所以梯度必须累加，而不能覆盖。

这不是 Python 实现上的细节，而是多元微积分中的链式法则和求导加法法则在计算图中的具体体现。

## 六、generation、seen_set、weakref 为什么都需要？

理解了上面的反向传播过程，这几个设计就非常自然了。

### generation：确保反向传播的处理顺序

继续看我们的例子：

$$y=b+a,\quad b=a^2,\quad a=x^2$$

变量代数为：

| Variable | generation |
| -------- | ---------- |
| x        | 0          |
| a        | 1          |
| b        | 2          |
| y        | 3          |

而 Function 的 `generation` 取输入变量中的最大代数。

你通过：

```
funcs.sort(key=lambda x: x.generation)f = funcs.pop()
```

让代数最大的 Function 优先执行。

为什么？

因为对于一个存在分支的计算图，必须尽可能等某个变量从下游接收完梯度，再使用这个变量的梯度继续向前传播。

例如，如果 `a` 的梯度还没有从 `b` 这条路径累加回来，就提前处理创建 `a` 的 Mul，那么得到的 `x.grad` 就可能遗漏部分贡献。

`generation` 帮助我们保证从深到浅的处理顺序。

### seen_set：防止重复调度同一个 Function

同一个 Function 的输出可能被多条路径使用。

如果每发现一条路径，就把这个 Function 加入待处理队列，很可能重复执行它的 `backward()`。

`seen_set` 记录哪些 Function 已经加入过队列，确保每个节点只被调度一次。

注意：

同一个 Function 只执行一次，不等于某个 Variable 的梯度只累加一次。

变量可以从多个输入位置或多个 Function 接收梯度。

### weakref：管理计算图对象的生命周期

你的 `Function.__call__()` 中：

```
self.inputs = inputs
self.outputs = [weakref.ref(output) for output in outputs]
```

输入用强引用，输出用弱引用。

这是因为反向传播时，需要能够从 Function 找到原来的输入数据。

而输出变量通过 `creator` 已经能够找到创建自己的 Function：

```
输出 Variable
    │
    │ creator（强引用）
    ▼
  Function
    │
    │ outputs（弱引用）
    ▼
输出 Variable
```

弱引用避免这里形成强引用环，并且不会仅仅因为 Function 保存了 outputs 而延长输出对象的生命周期。

这是内存管理方面的设计；它并不负责链式求导，也不负责计算图的排序。

你可以把这些功能分开记忆：

| 机制           | 解决的问题          |
| ------------ | -------------- |
| `creator`    | 怎么找到上一个计算节点？   |
| `generation` | 应该先处理哪个计算节点？   |
| `seen_set`   | 怎样避免重复调度？      |
| `grad` 累加    | 多条路径的梯度怎样汇总？   |
| `weakref`    | 怎样避免不必要的对象强引用？ |

把这几个问题分别想清楚，`backward()` 就不再是一段复杂的循环，而是一套目标明确的图遍历算法。

## 七、到了第三阶段，为什么只有一点修改就能支持高阶求导？

这是我认为你应该特别欣赏 DeZero 设计的地方。

第一、二阶段，我们已经实现：

```
Variable + Function + backward
```

这套框架能够计算一阶导数。

第三阶段需要二阶导数。

直觉上，你可能会想：是否需要再设计 `SecondOrderVariable`、`SecondOrderFunction`，甚至再编写一套二阶反向传播算法？

其实完全不需要。

因为有一个关键事实：

求导的过程本身也是由乘法、加法、幂运算等基本运算构成的。

例如：

$$y=x^4$$

第一次求导：

$$g_x=4x^3$$

`4*x**3` 本身仍然是一个数学表达式，可以被你的 Variable / Function 系统执行。

所以只需要在计算梯度时，让框架继续记录这次计算的过程。

这就是：

```python
with using_config('enable_backprop', create_graph):
    gxs = f.backward(*gys)
```

对应两种情况：

|                 | `create_graph=False` | `create_graph=True` |
| --------------- | -------------------- | ------------------- |
| 计算一阶梯度          | 是                    | 是                   |
| 梯度以 Variable 保存 | 是                    | 是                   |
| 为梯度运算建立计算图      | 否                    | 是                   |
| 可以沿梯度图继续求二阶导    | 否                    | 是                   |

这里需要特别理解：梯度是 Variable，不意味着梯度一定有计算图。

`gx.data` 可能都是 32，但只有记录了其计算来源的 `gx` 才能继续向原来的 `x` 传播梯度。

这也正是为什么你在 `Pow.backward()` 中需要：

```
x = self.inputs[0]
```

而不是：

```
x = self.inputs[0].data
```

前者保留原来的 Variable 依赖关系，后者只取得 NumPy 数值。

从一阶自动微分到高阶自动微分

原始计算图

$x\longrightarrow x^4\longrightarrow y$

第一次反向传播

$g_x=4x^3$create_graph=True：记录 4x³ 是如何计算的

梯度计算图

$x\longrightarrow 4x^3\longrightarrow g_x$

第二次反向传播

$\frac{dg_x}{dx}=12x^2$

你会发现，这里形成了一个很漂亮的结构：

用自动微分框架执行求导计算，再对求导计算的结果执行同一个自动微分框架。

这叫做机制的复用。

也正因为 Variable / Function 最初的抽象足够简洁，高阶自动微分才没有迫使我们推翻原有架构。

不要背 300 行代码。

你只需要在脑海中想象以下过程：

第一层：数值层

NumPy 负责真正执行数组加减乘除，Variable 包装 NumPy 数组。

第二层：记录层

Function 每执行一次，就保存输入、输出依赖和 `creator` 关系，于是形成计算图。

第三层：求导层

每个 Function 知道局部求导规则，Variable.backward() 按顺序调度这些节点并累加梯度。

第四层：高阶层

让梯度计算本身也使用 Variable / Function 建立计算图，从而可以再次调用 backward()。

## 十、我最希望你记住的本质

整个 DeZero 框架，可以浓缩成三个观点：

第一，Variable 是携带计算历史的数值。 它让计算结果不再是孤立的数字，而是可以追溯来源的节点。

第二，Function 是局部运算规则和局部求导规则的统一体。 复杂数学公式不需要整体求导，只需要把基本运算的导数按照链式法则连接起来。

第三，自动微分框架本质上是一套计算图记录和梯度传播机制。 前向执行建立依赖，反向遍历组合局部导数，而高阶求导只是进一步把梯度计算也纳入同一套机制。

所以，你目前写出来的 300 行左右的核心代码，真正厉害的地方不在于那些 `Mul`、`Pow`、`Add` 的求导公式，而在于：

> 你设计了一套机制，让任意数量的基本可微运算能够自动组合，并且无须事先知道最终数学表达式，就可以沿实际执行的计算路径完成求导。

这才是 Variable / Function 设计最值得掌握的思想。

接下来学 v0.4 的张量运算时，你会发现：虽然数据从标量扩展成了各种形状的张量，局部求导规则变复杂了，但是这套 Variable / Function 的核心关系基本不需要改变。
