### 两个值得注意的问题

1\. 广播梯度问题

例如：

```
x = Variable(np.array([1., 2., 3.]))b = Variable(np.array(2.))y = x + by.backward()
```

数学上，`b.grad` 应该是标量 `3.0`，但目前得到的是数组 `[1., 1., 1.]`。

这不是整个自动求导机制错误，而是还没有实现广播情况下的梯度归约（`sum_to`）。

我的建议： 如果 v0.2 主要处理标量运算，可以先不增加这套逻辑，但要明确记录这个限制。等学到张量运算时再补齐。

2\. Function 实例重复使用

```
f = Square()a = f(x)b = f(a)  # 当前实现不支持这样复用
```

因为 `Function.__call__()` 会修改实例中的 `inputs`、`outputs` 等信息，第二次调用会覆盖第一次保存的计算关系。

正确且符合当前设计的使用方式是：

```
a = square(x)b = square(a)
```

每次 `square()` 都创建一个新的 `Square()` 实例。

这也解释了为什么那些看似多余的函数包装其实很重要。

## 三、从一行代码开始，完整走一遍

假设我们计算：
$$
y=3(x^2+x),\quad x=2
$$

对应代码：

```python
x = Variable(np.array(2.0))
a = x * x
b = a + x
y = 3 * b
y.backward()
print(y.data)  # 18.0print(x.grad)  # 15.0
```

这段代码就是整个框架的缩影。

### 第一步：创建 Variable

```
x = Variable(np.array(2.0))
```

想象每个 `Variable` 都是一张卡片，里面有几个格子：

Variable: x

初始变量

| data       | 2.0    |
| ---------- | ------ |
| grad       | `None` |
| creator    | `None` |
| generation | `0`    |

`data` 是数字，`grad` 是将来反向传播获得的梯度，`creator` 记录谁产生了它，`generation` 则记录它位于计算图的哪一层。

Variable 的核心价值就是：给普通数字增加计算历史和梯度。

### 第二步：执行 x \* x

```
a = x * x
```

这一步看似简单，背后发生了五件事。

首先，`__init__.py` 在导入时执行 `setup_variable()`，将乘法运算符绑定到 `mul()`。

于是：

```
x * x
```

等价于调用：

```
mul(x, x)
```

然后：

```
Mul()(x, x)
```

实际上执行的是 `Function.__call__()`，它负责：

1. 把输入统一成 `Variable`。
2. 提取输入中的 NumPy 数据。
3. 调用 `forward()`，实际计算 `2 * 2 = 4`。
4. 把结果包装为新的 `Variable`。
5. 记录输入、输出、`creator` 和 `generation`。

于是产生了：

x

2.0

Mul

forward

a

4.0

Mul 的两个输入都指向同一个 x

新的 `a.creator` 指向刚刚创建的 `Mul` 对象；这个 `Mul.inputs` 则保存对 `x` 的引用。

注意这件事：

前向计算不仅产生了数字 4，还把计算来源一起记录了下来。

这就是动态图的本质。

### 第三步：连续运算，自然形成计算图

当继续执行：

```
b = a + x
y = 3 * b
```

框架就会形成下面这张图。

示意图：蓝色是 Variable，绿色是 Function。最后的 ×3 产生 y=18（gen 3）。

你会发现，代码里根本没有 `Graph` 类。

因为计算图不是预先建好的容器，而是由 Variable 和 Function 之间的引用关系自然形成的。

这也是 DeZero 设计非常值得学习的地方。

### 第四步：调用 backward，开始倒着走

```
y.backward()
```

前面所有计算都是从左到右，现在方向反过来。

先给输出设置梯度：

$$
\frac{\partial y}{\partial y}=1
$$

接着从 `y.creator` 找到最后一个乘法函数。

整个倒推过程如下：

① 从 y 出发

y.grad = 1

$$
y=3b,\qquad \frac{\partial y}{\partial b}=3
$$

得到 `b.grad = 3`。

② 经过 Add

b = a + x

梯度沿两条边分别传递：`a.grad = 3`，`x.grad = 3`。

③ 经过 Mul

a = x \* x

两个输入都是 `x`，所以贡献两份梯度：`3 × 2 = 6` 和 `3 × 2 = 6`。

④ 累加到 x.grad

# 3 + 6 + 6 = 15

反向传播结束

这段推导，你必须真正掌握。

因为以后神经网络哪怕有几百万个参数，其基本原理仍然是：局部求导、链式相乘、分支累加。

### 第五步：理解 backward 为什么要有调度机制

你的 `backward()` 不只是简单地调用每个 `Function.backward()`。

它还包含三个非常重要的设计：

`funcs` 是待处理的函数列表，`seen_set` 避免函数被重复加入，`generation` 决定处理顺序。

特别是当计算图有多个分支时，必须先等待所有下游梯度贡献完成，再继续向上游传播。

还有两个容易忽略的细节：

`retain_grad=False` 会清理中间变量的梯度，以减少内存占用。`weakref` 则用于弱引用函数的输出，避免不必要的强引用循环；`output_specs` 保留输出形状和类型，以便未使用的输出能够按零梯度处理。

core_simple.py



它们并非毫无意义的复杂代码。尤其是 `generation` 和梯度累加，属于自动求导引擎的重要组成部分。

## 四、再回过头看所有函数，各自负责什么

| 代码                    | 一句话理解                     |
| --------------------- | ------------------------- |
| `Variable`            | 装数据、梯度和计算来源               |
| `Function`            | 统一管理一次运算的前向与反向            |
| `Add/Mul/Sub/Div/Pow` | 具体运算与局部求导规则               |
| `as_array()`          | 将标量转换为 NumPy 数组           |
| `as_variable()`       | 将数据统一包装成 Variable         |
| `setup_variable()`    | 让 `x + y` 这样的 Python 写法生效 |
| `generation`          | 控制反向传播顺序                  |
| `weakref`             | 避免不必要的强引用循环               |
| `cleargrad()`         | 清空之前计算的梯度                 |
| `no_grad()`           | 前向计算时不记录计算图               |
| `__init__.py`         | 对外暴露接口，完成初始配置             |

这里还有一件值得记住的事：

你的 `Function` 子类并不需要管理整个计算图。

例如 `Mul`：

```python
class Mul(Function):
    def forward(self, x0, x1):
        return x0 * x1
    def backward(self, gy):
        x0, x1 = self.inputs[0].data, self.inputs[1].data
        return gy * x1, gy * x0
```

它只需要知道乘法怎么计算，以及乘法怎么求导。

至于输入包装、保存计算关系、反向遍历、梯度累加，全都交给公共基础设施。

这种分工相当优雅，也是我不建议你继续压缩框架核心结构的原因。

## 五、我建议怎么精简

### 值得做：删掉重复的 as_array

例如原代码：

```
def add(x0, x1):
    x1 = as_array(x1)
    return Add()(x0, x1)
```

实际上可以写成：

```
def add(x0, x1):
    return Add()(x0, x1)
```

因为 `Function.__call__()` 已经调用：

```
inputs = [as_variable(x) for x in inputs]
```

而 `as_variable()` 内部会使用 `as_array()`。

同样的精简适用于 `sub`、`rsub`、`mul`、`div`、`rdiv`。

这是删除真正的重复代码，值得做。

其他可以顺手处理的地方包括删除已经注释掉的旧 `gys` 实现、删掉注释状态的 `__mul__` 方法，以及将 `Function(object)` 改成 `Function`。

### 不值得做：为了短而合并基础运算

从数学上说，减法可以通过加法和负数实现，除法也可以利用乘法和幂实现。

但我不建议因此删除 `Sub`、`Div`、`Neg` 等类。

因为对于 LearnDL：

看见每个运算符对应的 forward 和 backward，比减少二三十行代码更有教学价值。

同样，我也不建议现在引入高级调度器、多层抽象基类或优化反向传播队列的数据结构。

当前 `funcs.sort()` 的性能不是这个阶段的主要问题。

## 六、哪些东西故意还没有实现？

你现在的 `core_simple.py` 是一个基础的反向模式自动微分引擎，而不是完整的深度学习框架。

最明显的特点是：当前 `grad` 保存 NumPy 数组，`backward()` 内部的求导计算也直接使用 NumPy。

这意味着当前实现不能自动为求导过程再构建一张支持高阶导数的计算图。

此外，广播梯度归约、矩阵乘法、参数管理、优化器等内容，也还没有在这两个文件中实现。

这正好符合循序渐进的学习目的，不应把未来的所有功能提前塞进 v0.2。
